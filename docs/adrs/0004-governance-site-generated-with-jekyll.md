# ADR 0004: Governance Site Generated with Jekyll

## Date

2026-09-29

## Context

[ADR 0002](./0002-schema-validated-yaml-governance-documents.md) moved the governance documents to schema-validated YAML so that overviews and HTML can be generated from them. Nothing generated them: the `Publish Schemas` workflow copied the JSON Schemas to GitHub Pages and stopped there. The semgrep rules in `thruput-io/semgrep` cite our rules by anchor, such as `#no-suppressed-exit-status`, and a YAML file serves no anchors.

The organisation site `thruput-io/thruput-io.github.io` is served at `https://thruput.se/`. GitHub serves every project site of the organisation under that custom domain at `https://thruput.se/<repository>/`, and the path segment is the repository name ([About custom domains and GitHub Pages](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages#using-a-custom-domain-across-multiple-repositories)). A site published from this repository is therefore `https://thruput.se/agents/`; `https://thruput.se/schemas/agents/` is only reachable from the organisation site repository.

## Decisions

- The site is published from this repository at `https://thruput.se/agents/`, and every schema `$id` moves under `https://thruput.se/agents/schemas/`, the address at which it is served.
- The site is generated by Jekyll, the generator GitHub Pages provides, with the image behind [`actions/jekyll-build-pages`](https://github.com/actions/jekyll-build-pages) pinned by digest. `scripts/site.sh` runs that image locally and in both workflows, so one build meets one bar wherever it runs.
- The pages, layout, and styling live in `web/`. The build mounts the entries of `web/`, `governance/` as Jekyll's data directory `_data` ([Data Files](https://jekyllrb.com/docs/datafiles/)), and `schemas/` read-only into one source directory inside the container, so the documents are read where they live and nothing is copied or committed.
- The build writes the site to a Docker volume and never into the repository. `scripts/site.sh` copies the rendered site to a directory when given one, which is how the `Publish Site` workflow gets what it uploads.
- One template renders an entry of any level and includes itself for the level below, walking the levels of `ImperataDerivata.yaml`. The document of a level is named by its id in the plural, `Axiom` in `Axioms.yaml` under `axioms`.
- One page renders the taxonomy as a tree from values down to standards, with the level criteria, an index per level, the glossary, and the schemas. The anchor of an entry is its id lowercased with apostrophes dropped and every other run of punctuation or spaces replaced by one hyphen, which is the anchor the semgrep rules already cite. A `[[Id]]` reference in prose becomes a link to that anchor.
- The brand stylesheet is the organisation site's, taken as a remote theme pinned to a commit; the layout and the tree styling are this repository's own.
- The generated HTML is checked by the [Nu HTML Checker](https://github.com/validator/validator) and every link and fragment by [lychee](https://github.com/lycheeverse/lychee), so an id declared twice, a reference to a missing entry, and an entry whose parent does not exist each fail the build. The schemas cannot express these cross-document properties.
- Standards enforced by linters live in `thruput-io/semgrep`, and the bottom level of the taxonomy links there.

## Consequences

### Positive
- A rule has a stable address that other repositories cite, and a reader sees the whole chain from a value to a standard on one page.
- Three defects the schemas cannot catch now stop the line before merge.

### Negative
- The build needs network access to download the remote theme.
- The plural naming of a level's document is a convention of the template that no schema enforces.
- A file added to the root of `web/` is mounted by name, so the site is built the same way only through `scripts/site.sh`.
